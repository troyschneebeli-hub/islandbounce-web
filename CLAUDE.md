# Island Bounce Travel (islandbouncetravel.com): project notes

Next.js 14 (app router) ferry-comparison affiliate site on Vercel. Owner: Troy (ClankINC partner). Earns via 12Go affiliate.

## Site address
- The live site is `https://www.islandbouncetravel.com` (Vercel 308-redirects the bare domain to it). `SITE_URL` in `lib/site.js` must stay the www address: canonicals, sitemap, robots and JSON-LD all come from it. Search Console: use the www sitemap URL.

## Money and links
- 12Go affiliate ID `17069158` (param `z`), `sub_id=islandbounce-web`. White label: `https://booking.islandbouncetravel.com`.
- Links are built in `lib/affiliateLinks.js` / `lib/bookingLink.js`: `/en/travel/<from>/<to>?date=&date2=&people=&adults=`. Slug quirk: our `benoa-nusa-dua` redirects to 12Go's `tanjung-benoa-nusa-dua`; confirm `z` survives the redirect.
- 12Go has no open API. Never call 12Go's internal endpoints (e.g. `/api/nuxt/.../tripsV2/search`). Official option (12Go support, 19 Oct 2026): the partner **Timetable Service**, a PHP library `timetable.php` (dashboard > Timetable > Integration, downloadable only when logged in), `get12GoTimetable(country, from, dest, class, noreturn, lesslinks, lang, curr)` returning HTML. We run Next.js on Vercel (no PHP); Troy is asking 12Go for the endpoint/parameters or the file. Route/operator URL parameters are NOT supported; dashboard > Links makes verified route deep links.
- Per-sailing deep links are NOT possible: "Book now" is an add-to-cart button, checkout URLs are cart IDs. Time chips link to the route page with date/travellers prefilled. Ask 12Go about trip-level links.
- Never click Book now / add to cart on the live booking site to test.

## Timetable data (operator timetables since 27 Oct 2026)
- **12Go said no (27 Oct 2026):** no approval to scan their site, no data feed, an API only above ~US$15k/month in sales. Their terms (12go.asia/en/terms §9.3 a, c) forbid scrapers and commercial reuse of their content. So the site shows NO 12Go times or fares, and nothing automated may open 12Go or booking.islandbouncetravel.com pages. The 12Go scan (scan_12go.mjs, match.py, window.mjs, build-confirmed.mjs, data/generated/, data/confirmed.js, data/typical.js) is retired history: don't revive it. Its workflow was deleted.
- **Source of truth: `data/operator-sailings.json`** (each operator's own published timetable, edited by hand) + `data/operator-sailings-checked.json` (`checked`: the date someone last went through the rows against the operators' pages; the site shows "checked <date>" and warns visitors after 21 days, `STALE_AFTER_DAYS`) + `data/bookable-pairs.json` (operator + port pairs bookable on our booking site, frozen from the 22-28 Oct 2026 scan, plus `seenDaily` times; add a pair by hand after seeing it on the booking site yourself).
- `node scripts/build-timetable.mjs` writes `data/timetable.js` (AUTO-GENERATED: `TIMETABLE_CHECK`, `DAILY_SAILINGS`, `OTHER_SAILINGS`). A row is daily (route pages) when its pair is bookable and the operator says daily, or names no days and the time was in `seenDaily`. Other rows on bookable pairs are Trip Planner only, "Typical, check live times". Reseller/assumed rows are never daily. Operators not bookable on our booking site aren't shown. Drops impossible arrivals and check-in notes naming another port's office, and prints them (the operators' pages are messy: many arrivals are wrong; Scoot publishes none). Season notes in `days` ("Oct '26", "Nov '26 to Apr '27") become validFrom/validTo (BlueWater switches timetable 1 Nov). `NAMES` maps operator-sailings names to the site names (keeps operator page URLs). Node only.
- **After editing operator-sailings.json:** update `checked`, run `node scripts/build-timetable.mjs`, then `npm run build` and `node scripts/check-data.mjs`.
- No fares anywhere (no "From A$" column, no "Cheapest" pick): the booking page has live fares. No "Confirmed" tag (every row is from the operator). Rows have `confidence: "operator"`.
- Route pages: one open table of daily sailings; pairs with none get a "Check live times" box, never invented times. An existing page with none stays up with that box; `check-data.mjs` prints a `WARNING:`; more than max(5, 15% of pages) fails.
- `data/sailings.js`: `SAILINGS` = DAILY_SAILINGS (route pages, hub, sitemap); `PLANNER_SAILINGS` = SAILINGS + OTHER_SAILINGS. Import from there only. `data/twelvego.js`, `data/timetables.js`, `data/confirmed.js`, `data/typical.js` and the xlsx files are research files: nothing in `app/` or `components/` may import them.
- `node scripts/check-data.mjs` (after `npm run build` it also reads the built route pages): every row is on an operator timetable and a bookable pair, route-page rows are daily, no fares, no duplicate ids, ports exist, every row carries the check date (not in the future), each page renders exactly its daily rows and count, no Confirmed tag or A$ fare.
- `data/planner.js` BOAT_ROUTES decides which port/destination pairs the Trip Planner offers. Only list pairs that have sailings.

## Checks and automation
- `.github/workflows/weekly-operator-check.yml` (Mondays 02:00 UTC, `scripts/weekly/operator_watch.mjs`, pages in `scripts/weekly/operator-pages.json`) reads 20 operators' own timetable pages once a week (read-only, honest user agent, robots.txt respected) and emails what changed since last week and which of our listed times are no longer on the operator's page. It never edits the list: update operator-sailings.json from the report (or ask Claude), then bump `checked`. BlueWater (images) and booking-engine-only operators (D'Camel, WaterJet, Wahana, Golden Queen, Arthamas, Dream Beach, Nusa Nadhi, Tanis ModernDream, Wijaya Tramena) aren't checked: check them by hand now and then.
- `.github/workflows/weekly-link-check.yml` (Wednesdays 01:00 UTC, `scripts/weekly/check_links.mjs`, read-only, OUR site only): every sitemap page loads, route pages have rows or the "Check live times" box, and every booking link has `z=17069158` and `sub_id`, our booking host, `/en/travel/<from>/<to>` with port slugs from data/ports.js, and sane date/travellers. (Checked by hand 22 Oct 2026: 12Go strips z/sub_id from the address and keeps them in cookies named `z` and `sub_id`.) Problems open an issue.
- `.github/workflows/pr-check.yml`: on every PR, `npm ci`, data checks, parser tests, `npm run build`, rendered-page checks.

## Site pages and assets (27 Oct 2026)
- Home (`app/page.js`): search-first. Hero photo (HeroBand), booking box, stats and "Popular routes" (top 6 route pages by daily boats) all computed from SAILINGS; harbour guides; trip planner link.
- Port guides `/indonesia/ports/<slug>` (`app/indonesia/ports/[slug]/page.js`, logic in `lib/portPages.js`): one per port with at least one daily sailing in or out (`PORT_PAGE_SLUGS`, currently 9; Serangan/Kusamba appear once they have daily boats). Daily boats from/to the port per destination (count, first-last, fastest crossing, lowest fare) linking to route pages, booking box starting from that port, getting there + Google Maps, sea conditions, BoatTerminal JSON-LD. In the sitemap.
- Route pages (36): 22 hand-written in `data/routePages.js` (group pages like "Bali to the Gili Islands" plus the main one-pair pages) and 14 one-port-to-one-port pages built from the `SPECIFIC` list (`specificRoute`, port copy in `PORT_NOTES`, a hand-written `about` per page). A pair only gets its own page with 4+ daily boats (one or two boats is thin and empties when one operator drops out). Group pages show a "<name> by port" block linking down (`specificPagesIn`); `routePageFor` picks the most specific page everywhere. The /indonesia hub lists the top 10 by daily boats.
- Operator pages `/indonesia/operators/<slug>` (`lib/operatorPages.js`): one per operator with 3+ daily sailings (`OPERATOR_MIN_DAILY`), computed from SAILINGS, with a visible "independent comparison site, not <operator>" note and the operator's own domain (`OPERATOR_SITES`, nofollow). Never use operator logos or photos, never imply we're the operator. Route pages' operator chips link to them.
- Planning guides `/indonesia/guides/<slug>` (`data/guides.js`): Ubud / Seminyak-Canggu / airport to the Gilis, Padang Bai vs Sanur. Boat numbers come from `boatStats` (SAILINGS); drive times are the same rough ranges the port pages use (Padang Bai is 1 to 1.5 h from Kuta, not 45 min).
- Keyword research (Mangools, 27 Oct 2026, worldwide/month): "gili to bali" 12.2k, "bali to gili" 7.8k, "bali to lombok ferry" 6.1k, "eka jaya fast boat" 9.1k, "wijaya buyuk" ~8k combined, "fast boat nusa penida" 2.4k, "sanur to nusa penida" 1.7k, "ubud to gili" 1.4k, "nusa penida to gili" 1.1k. People write "Gili T" and "ferry", so titles use both.
- Photos go through Next's optimiser via `lib/img.js` (`optimized`, `srcSetFor`) on the plain `<img>` tags (PlacePhoto, HeroBand, RegionCard, PhotoStrip, PortsExplorer): ~75-80% smaller WebP on phones. Pass `sizes` for small slots.
- Fonts are self-hosted: `app/fonts.css` + `public/fonts/*.woff2` (Latin subset, same family names as the old Google Fonts link, Big Shoulders and Inter are variable files). No request to fonts.googleapis.com.
