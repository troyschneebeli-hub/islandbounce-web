# Island Bounce Travel (islandbouncetravel.com): project notes

Next.js 14 (app router) ferry-comparison affiliate site on Vercel. Owner: Troy (ClankINC partner). Earns via 12Go affiliate.

## Site address
- The live site is `https://www.islandbouncetravel.com` (Vercel 308-redirects the bare domain to it). `SITE_URL` in `lib/site.js` must stay the www address: canonicals, sitemap, robots and JSON-LD all come from it. Search Console: use the www sitemap URL.

## Money and links
- 12Go affiliate ID `17069158` (param `z`), `sub_id=islandbounce-web`. White label: `https://booking.islandbouncetravel.com`.
- Links are built in `lib/affiliateLinks.js` / `lib/bookingLink.js`: `/en/travel/<from>/<to>?date=&date2=&people=&adults=`. Slug quirk: our `benoa-nusa-dua` redirects to 12Go's `tanjung-benoa-nusa-dua`; confirm `z` survives the redirect.
- 12Go has no open API. Never call 12Go's internal endpoints (e.g. `/api/nuxt/.../tripsV2/search`). Official option (12Go support, 19 Oct 2026): the partner **Timetable Service**, a PHP library `timetable.php` (dashboard > Timetable > Integration, downloadable only when logged in), `get12GoTimetable(country, from, dest, class, noreturn, lesslinks, lang, curr)` returning HTML. We run Next.js on Vercel (no PHP); Troy is asking 12Go for the endpoint/parameters or the file. Route/operator URL parameters are NOT supported; dashboard > Links makes verified route deep links.
- Per-sailing deep links are NOT possible: "Book now" is an add-to-cart button, checkout URLs are cart IDs. Time chips link to the route page with date/travellers prefilled. Ask 12Go about trip-level links.
- Never click Book now / add to cart on the live booking site to test.

## Timetable data (decided 22 Oct 2026)
- **Route pages: every DAILY sailing you can book (decided 24 Oct 2026; was confirmed daily only).** Daily = listed on the 12Go booking page on at least 6 of the 7 nights in the window (12Go hides sold-out trips for a night). Rows that also match the operator's own timetable (same operator + route + departure within 10 min) are `confidence: "confirmed"` and tagged **Confirmed** in the table (operator's time); 12Go-only daily rows are `confidence: "listed"` (12Go's time). A 12Go-only listing of the same operator within 10 min of one already shown is the same boat and is merged (match.py `daily-sailings.json`). Shown with 12Go's lowest A$ fare (1 adult). One open table, no drop-downs, no "typical" block. Pairs with none get a "Check live times" box, never invented times. New route pages are only added for pairs with at least one daily sailing. An existing page that has none in a given week (decided 23 Oct 2026) stays up with the "Check live times" box and no table, so Google never sees it come and go; `check-data.mjs` prints it as a `WARNING:` and the weekly email lists it. More than 5 such pages fails the check (the data probably went wrong).
- **Trip Planner / port cards / ports map:** confirmed daily first, tagged "Confirmed", then 12Go-only daily ("Daily"), then the rest labelled "Typical, check live times" (not daily: shown only on the weekdays seen). Operator-only sailings are never shown.
- Source of truth: `data/generated/` (the matcher's output): `daily-sailings.json` (what the route pages show; safety checks and emails compare it), `confirmed-sailings.json`, `confirmed-daily-sailings.json`, `twelvego-only-sailings.json` (+ `scan-health.json`, `report.md`, `diff.md`). Data from before 24 Oct 2026 has no `daily-sailings.json`: everything falls back to the confirmed daily file. Seeded 22 Oct 2026 from the manual 22-28 Oct scan and the 20 Oct 12Go capture (D'Camel and Rocky left out of the seed).
- `node scripts/build-confirmed.mjs` turns `data/generated/*.json` into `data/confirmed.js` (CONFIRMED_DAILY, LISTED_DAILY, CONFIRMED_NOT_DAILY, CONFIRMED_SCAN) and `data/typical.js` (TYPICAL_SAILINGS), both AUTO-GENERATED. It drops impossible arrivals (falls back to 12Go's arrival), check-in notes naming another port's office, and confirmed rows whose source says UNCONFIRMED (reseller), and prints all of it. `INCLUDE_SIX_OF_SEVEN` (default false) would also list sailings seen on 6 of 7 days. Node only: Python isn't installed on Troy's laptop (the GitHub Action has it for match.py).
- `data/sailings.js`: `SAILINGS` = CONFIRMED_DAILY + LISTED_DAILY (route pages, hub, sitemap); `PLANNER_SAILINGS` = planner set. Import from there only. `data/twelvego.js`, `data/timetables.js` and the xlsx files are research files: nothing in `app/` or `components/` may import them.
- `node scripts/check-data.mjs` (after `npm run build` it also reads the built route pages): every listed row is in the daily file, no duplicate ids, ports exist, rows have operator/departs/price, dates not later than the check date, each page renders exactly its daily rows and count, no collapsed/typical block.
- Dates on the site: "checked <generatedAt date> for sailings <scan window>", computed from the data. No "every week"/"monthly" claims until the weekly job has run live.
- `data/planner.js` BOAT_ROUTES decides which port/destination pairs the Trip Planner offers. Only list pairs that have sailings.

## Timetable automation (daily from 24 Oct 2026; NOT yet published live; nightly schedule PAUSED 25 Oct 2026)
- **Paused:** once the scanner stopped disguising itself (23 Oct), 12Go serves it a "0 trips" page on every route whose title still advertises a fare ("... from IDR 373,750"): a soft refusal. The scanner now treats that as a failed load (`showsNoTrips` in scan_12go.mjs) and stops the night after 3, and the daily workflow only runs by hand. Do NOT re-add a fake user agent or anti-detection flags. Resume (uncomment the cron) only once 12Go allows the scanner or offers a feed; then re-seed the window, because the 24 Oct scans stored empty readings for 18 routes.
- `.github/workflows/daily-timetable.yml`, every night 17:00 UTC (01:00 Bali). See TIMETABLE_AUTOMATION.md. Scans ONE date 3 days ahead (`scripts/weekly/scan_12go.mjs`, Playwright, read-only), puts it in that weekday's slot of the window (`scripts/weekly/window.mjs`: one slot per weekday; a route that fails tonight keeps its last good reading up to 14 days old; stored with the weekly reference as the `scan-window` artifact), and once all 7 weekdays are filled: `match.py` -> `changes.mjs` -> `publish_check.py` safety gate -> `build-confirmed.mjs` -> `check-data.mjs` -> commit + push to main. Replaced the weekly Tuesday run (7 dates at once set off 12Go's bot check). Emails only on real changes, blocks or a broken run (see TIMETABLE_AUTOMATION.md).
- Card parsing lives in `scripts/weekly/parse_card.mjs`; `node scripts/weekly/test_parse.mjs` tests it against real cards. 12Go serves two layouts: A (seen in a normal browser) `dep | arr | duration | from station | to station | [seats] | class | Ferry | operator | rating | A$price`; B (what GitHub's runner gets) `dep | from station | duration | operator | Ferry | class | arr | to station | rating | price`. Multi-leg trips are dropped ("Van+Ferry" type, or a class like "Fast Ferry + Van"). The scanner adds `curr=AUD` (without it the US runner gets US$); a non-A$ price is stored as null, never misread. 12Go route pages also list trips from nearby ports (Bangsal pages show Gili T / Gili Air boats): `stationFits` drops a trip whose from/to station names a different port (unrecognised station names are kept); the log says how many were left out. When a route has cards but 0 ferries, the scan log prints 3 raw cards: re-capture fixtures from there if 12Go changes the layout.
- `data/operator-sailings.json` (613 operator timetable rows) is updated by hand. `.github/workflows/weekly-operator-check.yml` (Mondays 02:00 UTC, `scripts/weekly/operator_watch.mjs`, pages in `scripts/weekly/operator-pages.json`) reads 20 operators' own timetable pages once a week (read-only, honest user agent, robots.txt respected) and emails what changed since last week and which of our listed times are no longer on the operator's page. It never edits the list. BlueWater (images) and booking-engine-only operators (D'Camel, WaterJet, Wahana, Golden Queen, Arthamas, Dream Beach, Nusa Nadhi, Tanis ModernDream, Wijaya Tramena) aren't checked. `scripts/weekly/routes.json` (68 pairs) must include every from/to pair in it, or those sailings can never be confirmed.
- 12Go's bot check (HTTP 405, "Human Verification" page) started a few minutes into each day when 7 scans ran at once (23 Oct 2026). The scanner records it as a FAILED load (never "no boats"), pauses 8 s between routes and 5 min after a check, gives up the night after 3 checks in a row, and only one date is scanned per night. An empty page that isn't 12Go's own "0 trips" timetable also counts as a failed load. Each night has a 100-minute budget (`SCAN_BUDGET_MIN`) under the job's 120-minute limit: routes not reached are recorded as failed, so a slow day never gets the job cancelled (a cancelled scan job skips matching for the whole week). It uses Playwright's own browser identity: never disguise the scanner or try to get past the check. If it keeps blocking, ask 12Go to allow it or use their partner Timetable Service.
- `build-confirmed.mjs` takes "daily" from match.py's `runsDaily` (which allows one day that failed to load), not from counting days seen.
- Weekly reference: after a publish, if the reference is 7+ days old, a "Weekly timetable summary" issue lists the week's changes and tonight's data becomes the new reference; `publish_check.py --baseline` also blocks a >30% drop against it (catches slow slides). Emails also list boats seen on 12Go 6+ of 7 nights that aren't in operator-sailings.json (add them by hand). The site's "checked" date is the latest nightly check (match.py generatedAt = newest scan).
- Email (issues that @mention the owner): "Timetable updated" when a publish added/removed sailings or operators (`changes.mjs --flags` decides; price-only changes send nothing), comments on the open "Timetable update blocked" / "Daily timetable run failed" issues otherwise. Body built by `scripts/weekly/changes.mjs` (counts, operators gone from/new on 12Go, sailings added/removed, price changes) plus the safety-check output and the route pages showing "Check live times". The workflow runs with `shell: bash` so piping a check through `tee` still fails the step.
- **12Go's terms (12go.asia/en/terms §9.3 a, c) forbid bots/scrapers and commercial reuse without written approval.** So nothing automated may open 12Go or booking.islandbouncetravel.com pages unless Troy gets written approval (the nightly scan is paused for this reason too). Operators' own sites are fine (robots.txt respected).
- `.github/workflows/weekly-link-check.yml` (Wednesdays 01:00 UTC, `scripts/weekly/check_links.mjs`, read-only, OUR site only since 27 Oct 2026): every sitemap page loads, route pages have rows or the "Check live times" box, and every booking link has `z=17069158` and `sub_id`, our booking host, `/en/travel/<from>/<to>` with port slugs from data/ports.js, and sane date/travellers. (Checked by hand 22 Oct 2026: 12Go strips z/sub_id from the address and keeps them in cookies named `z` and `sub_id`.) Problems open an issue.
- `.github/workflows/pr-check.yml`: on every PR, `npm ci`, data checks, parser tests, `npm run build`, rendered-page checks.
- The safety gate blocks the publish if a route loses >30% of its daily sailings, so a big operator disappearing from 12Go (seen 22 Oct: Wijaya Buyuk, Tanis not listed) will block every run until someone reviews and runs it with the drop accepted.
